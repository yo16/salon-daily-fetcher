## 0. 確定済みの前提（ヒアリング済み）

| 項目 | 確定内容 |
|---|---|
| ログイン種別 | 個人会員（メールアドレス + パスワードの直接ログイン） |
| ログイン経路 | `https://salon.jp/authentications/login`（Facebook認証は使わない） |
| 2段階認証/追加認証 | なし（ID/PW のみでログイン完了）→ 完全無人実行が可能 |
| 取得したい情報 | (1) 記事一覧のメタ情報（タイトル・日時・URL） / (2) 新着記事/投稿の本文テキスト |
| 取得範囲 | 当日から過去へ遡り、未取得分のみ取得（バックフィル対応・冪等） |
| 設計方針 | **特定サロン専用のシンプルな実装**（汎用エンジンは作らない）。壊れやすいURL/セレクタのみ薄い設定に外出し |
| 認証情報の方針 | **`.env.local`** に保存（推奨補強: 保存済みセッション優先 + 失効時のみ再ログイン） |
| 実装言語 | Python（Playwright for Python） |
| 書き込み方針 | 累積マージ（IDで重複排除、履歴保持） |
| 利用目的 | (1) 個人閲覧・アーカイブ / (2) 別システム（AI/LLM）への読み込み |
| 失敗時の通知 | なし（ログ＋終了コードのみ） |
| 画像/添付 | 対象外（本文テキストのみ取得） |
| 実行環境 | Windows PC、デスクトップ等のショートカットから手動起動、原則無人で完了 |

### 前提となる利用範囲（重要）
本ツールは **利用者本人が正規に閲覧権限を持つコンテンツを、私的にアーカイブ／閲覧効率化する目的** に限定する。
- コンテンツの再配布や第三者提供は行わない。
- 過剰アクセスを避ける（後述のスロットリング・1日1回運用・多重起動防止）。
- 利用規約・robots 等で禁止される行為は行わない範囲で実装する。

## 1. システムの目的

Salon.JP の会員ページに自動でアクセスし、毎日更新される記事一覧と本文テキストを取得して、ローカルに蓄積・アーカイブする個人/小規模向け自動化ツール。

- Windows ショートカットから起動 → 原則無人で取得・保存 → 終了
- 取得手順・対象ページは外部設定ファイル（YAML）で指定し、本体にハードコーディングしない
- 安定して毎日動作し、失敗時は原因をログで追跡できる

## 2. 想定ユーザーと利用シーン

- **ユーザー**: Salon.JP 個人会員本人（Windows、非エンジニア寄りでも設定編集できることを目標）
- **利用シーン**: ショートカットをダブルクリック → 無人でログイン→取得→保存 → 自動終了。日次1回程度。
- **失敗時**: ログファイルとスクリーンショットで原因確認。データは壊さない。

## 3. 機能要件（FR）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | `.env.local` から認証情報（メール/パスワード）を読み込む | 必須 |
| FR-02 | 保存済みセッション（Cookie/storage state）があれば再利用しログインを省略する | 推奨 |
| FR-03 | セッションが無効/未取得の場合、対象サロン向けのログインフローを実行して自動ログインする | 必須 |
| FR-04 | 対象サロン専用の取得処理（ログイン→一覧→本文）を直線的に実行する。URL/セレクタは `config.yaml` 参照 | 必須 |
| FR-05 | 記事一覧（タイトル・日時・URL）を抽出する | 必須 |
| FR-06 | 各記事の本文テキストを取得する（当日から過去へ遡り、未取得分のみ。上限件数で安全装置） | 必須 |
| FR-07 | 一覧を `index.json` に重複排除しながら累積マージする | 必須 |
| FR-08 | 本文を記事ごとに Markdown ファイルとして保存する（メタをフロントマター化、UTF-8） | 必須 |
| FR-09 | AI/LLM 取り込み用に全記事を集約した機械可読ファイル（JSONL: 1行1記事）を出力する | 推奨 |
| FR-14 | 本文はナビ/広告等の定型要素を除いたクリーンテキストとして抽出する（AI入力品質確保） | 推奨 |
| FR-15 | 任意で一覧を CSV にエクスポートする | 任意 |
| FR-10 | 実行ログをファイル＋コンソールに出力する | 必須 |
| FR-11 | 失敗時にスクリーンショット/HTMLダンプを保存する | 推奨 |
| FR-12 | 多重起動を防止する（ロックファイル） | 推奨 |
| FR-13 | URL/CSSセレクタを `config.yaml` に外出しし、サイト構造変更時はそこだけ修正すれば直せる | 推奨 |

### 処理フロー（特定サロン専用・直線的）
汎用アクション語彙は作らず、対象サロン向けの処理をスクリプトに直接記述する。Playwright の標準API（`goto`/`fill`/`click`/`wait_for_selector`/`inner_text`/`get_attribute` 等）を素直に使う。

1. `.env.local` から認証情報を読み込む
2. 保存済みセッションがあれば復元、なければログインフローを実行
3. 対象サロンの記事一覧ページを開き、各記事のメタ（id/title/date/url）を抽出
4. `index.json` と突き合わせ、当日から過去へ遡って未取得分を特定
5. 未取得記事の本文を取得（記事間はスロットリング）
6. `index.json` 累積マージ ＋ 本文 Markdown ＋ `corpus.jsonl` を出力
7. ログ出力、失敗時はスクショ/HTMLダンプ

> URL・CSSセレクタなど「サイト構造に依存し壊れやすい値」だけを `config.yaml` に外出しする（コードには直書きしない）。

## 4. 非機能要件（NFR）

| ID | 要件 | 実現方針 |
|---|---|---|
| NFR-01 | 個人/小規模利用・シンプルさ優先 | 単一プロセス・依存最小・特定サロン専用の直線的処理（汎用化しない） |
| NFR-02 | 毎日安定動作 | リトライ＋タイムアウト＋セッション再利用 |
| NFR-03 | サイト構造変更に追従しやすい | URL/セレクタのみ `config.yaml` に外出し、本体コードは非依存 |
| NFR-04 | 原因究明しやすい | 構造化ログ＋失敗時スクショ/HTMLダンプ＋Playwright trace |
| NFR-05 | ログを残す | `logs/run-YYYY-MM-DD.log`（日次ローテーション）＋コンソール |
| NFR-06 | 過剰アクセス回避 | リクエスト間スロットリング、1日1回運用、多重起動防止、セッション再利用 |
| NFR-07 | 規約/アクセス制限を尊重 | 本人閲覧範囲限定・再配布なし・robots尊重 |
| NFR-08 | 認証情報の安全な取り扱い | `.env.local` は `.gitignore`、リポジトリに含めない、`.env.local.example` を提供 |

## 6. 実装方式の決定

- **採用**: Playwright（Chromium headless）による、対象サロン専用の直線的なスクリプト。汎用ステップ実行エンジンは作らない。
- **設定の外出し**: 壊れやすいURL/CSSセレクタと最小限の動作設定のみ `config.yaml` に置く。
- **認証**: 保存済みセッション（storage state）を優先利用し、無効時のみ `.env.local` の ID/PW で自動再ログイン（ハイブリッド）。
- **却下/保留**: HTTP+HTML解析（ログインの安定性に難）／API直接（公開APIなし・規約リスク）／汎用YAMLエンジン（過剰設計）。

## 7. MVP（最小構成）

段階的に構築する。

- **Phase 1（MVP）**: `.env.local`読込 → ログイン（or セッション再利用）→ 対象一覧ページを開く → 記事一覧（タイトル/日時/URL）抽出 → `index.json` 累積マージ → ログ出力 → 失敗時スクショ。
- **Phase 2**: 未取得記事の本文を取得 → `articles/YYYY-MM-DD/<id>.md` 保存。
- **Phase 3**: CSVエクスポート、複数ジョブ対応、リトライ/スロットリング調整、（任意）通知。

## 9. 設定ファイル設計案

設定は2ファイルに分離する。**秘密情報は `.env.local`、それ以外（URL/セレクタ/動作設定）は `config.yaml`**。

### .env.local（認証情報・コミット禁止）
```
SALON_EMAIL=your_email@example.com
SALON_PASSWORD=your_password
```
- `.gitignore` に登録。`python-dotenv` で `load_dotenv(".env.local")` として読み込む。
- 雛形 `.env.local.example`（値は空）をコミットしておく。

### config.yaml（対象サロン専用の設定。コミット可）
```yaml
# --- 対象URL ---
login_url:   "https://salon.jp/authentications/login"
list_url:    "<対象サロンの記事一覧URL>"     # 実機確認後に確定

# --- CSSセレクタ（サイト構造に依存する壊れやすい部分のみ集約）---
selectors:
  login_email:    "input[name='email']"
  login_password: "input[name='password']"
  login_submit:   "button[type='submit']"
  logged_in_mark: "<ログイン後にだけ出る要素>"   # ログイン成否判定
  list_item:      "<記事カードのセレクタ>"
  item_link:      "<記事リンク a>"
  item_title:     "<タイトル>"
  item_date:      "<日時>"
  body:           "<本文コンテナ>"

# --- 動作設定 ---
headless: true
timeout_ms: 15000          # 要素待機の既定タイムアウト
throttle_seconds: 2        # 記事間の待機（過剰アクセス回避）
max_items_per_run: 50      # 1実行で取得する本文の上限（安全装置）
order: "newest_first"      # 当日から過去へ遡る
retry:
  max_attempts: 3
  backoff_seconds: 2
on_login_failure: "abort"      # abort | continue
on_element_missing: "skip"     # skip | abort
save_debug_on_error: true      # 失敗時にスクショ+HTMLダンプ
output_csv: false              # 一覧CSVエクスポートの要否
```

> `<...>` のセレクタは salon.jp の実画面をログイン後に確認して確定する。サイト構造が変わった場合も、本ファイルのセレクタを直すだけで復旧でき、本体コードは触らない。

### 出力設計（個人閲覧＋AI読み込みの両立）
利用目的が「個人アーカイブ」かつ「AI/LLMへの読み込み」のため、人向けと機械向けの両方を出す。

| 出力 | 形式 | 用途 | 備考 |
|---|---|---|---|
| `index.json` | JSON | 取得済み管理・重複判定のマスタ | `id` をキーに累積マージ |
| `articles/.../<id>.md` | Markdown(UTF-8) | 人が読む・差分管理 | フロントマターに `id/title/date/url/fetched_at` |
| `corpus.jsonl` | JSONL | AI/LLM一括取り込み（RAG等） | 1行1記事 `{id,title,date,url,body}`、本文はクリーンテキスト |

- 本文抽出時にナビ・広告・フッタ等の定型要素を除外し、AI入力品質を確保する（FR-14）。
- 文字コードは UTF-8 に統一する。

## 10. エラー処理とログ設計

### ログ
- 出力先: `logs/run-YYYY-MM-DD.log`（日次ローテーション）＋ コンソール。
- フォーマット: `時刻 | レベル | ステップ名 | メッセージ`。
- レベル: INFO（進行）/ WARNING（リトライ・軽微）/ ERROR（失敗）。
- 実行サマリを末尾に出力（取得件数・新規件数・所要時間・成否）。

### エラー方針
| 事象 | 挙動（既定） |
|---|---|
| ログイン失敗 | ERRORログ＋スクショ保存＋**非ゼロ終了**、データは更新しない |
| セッション失効 | WARNINGログ＋`.env.local` で自動再ログイン、ダメなら上記ログイン失敗扱い |
| 要素が見つからない/タイムアウト | 最大3回リトライ（指数バックオフ）→ なお失敗なら `on_element_missing` に従う（skip=部分成功保存 / abort=中断） |
| ネットワークエラー | リトライ対象 |
| 多重起動 | ロックファイル検出時は即終了（二重取得防止） |

### デバッグ容易性
- 失敗時に **スクリーンショット**＋**該当ページHTMLダンプ**を `logs/` または `data/debug/` に保存。
- Playwright **trace** を必要時に有効化（`trace=on-failure`）し、後から操作再生して原因特定。
